# Orca 基线上的有限接触面 Kernel：版本功能路线图

日期：2026-09-06
状态：功能规划提案；不是已实现功能清单，不是交付期限或性能承诺。

## 一、目标与编号

本规划将“第一版最小可行方案”命名为 v0.1；v1.0 表示在明确支持范围内，外部开发者能够持续使用，并有真实行业软件交付验证的稳定目标版。此前材料中的“V1 只做三个模块”对应这里的 v0.1，不应误读为首版要实现本文件全部功能。

建议主线：v0.1 最小闭环 → v0.2 可控内测 → v0.3 跨执行器与跨仓库复用 → v0.4 首个行业试交付 → v0.5 二次复用与维护 → v1.0 稳定目标版。

进化增强：v1.1 经验辅助与离线策略优化 → v2.0 有边界的候选探索和持续改进。

嵌入式是一条需求驱动的应用扩展线，不要求内核主线同时支持所有设备。先只读对接，再对具体板卡验证开发能力，控制动作另立验收门槛。

版本是验收节点，不是重建架构的次数。既有能力已经满足某项要求时，直接复用；相邻阶段可以合并交付，但不得跳过验证。

### v1.0 的目标

在声明支持的环境、执行器和仓库类型内，用户使用自己的模型账户和代码仓库，能够提出有限目标、确认分工，让独立 Agent 受约束地执行，取得通过验收的集成成果；出错时能够理解原因、停止、保留成果并恢复或人工接管。同时，至少有一个行业能力包完成真实交付，并经过第二次复用与升级验证。

它不是“任意行业、任意代码、任意设备、无限并发、无人监督”的承诺。

### 交付层次

| 层次 | 职责 | 边界 |
|---|---|---|
| Orca | 工作区、执行会话、消息、任务运行事实与已有恢复能力 | 不重写同义设施 |
| Kernel | 任务边界、必要交接、成果接纳与集成约束 | 不演变成新 IDE 或新调度平台 |
| 行业能力包 | 领域契约、可信模块、配置、样例与验收 | 先随项目存在，不先建设市场 |
| OpenDashboard / 行业软件 | 为实际使用者解决业务问题 | 不依赖 Orca 或开发 Agent 在客户环境持续运行 |

OpenDashboard 可以从 v0.1 开始作为真实开发仓库，但完整行业产品要求到 v0.4 才进入发布门槛。客户访谈、样例收集和验收定义现在即可进行，不等于同时开工建设所有功能。

## 二、复用边界

Orca 当前官方材料已提供并行 Worktree、多执行器接入、终端、Git 工作流、编排任务与消息等能力；编排指南还描述了 Worker 的读取、停止、释放及条件化恢复。[R1][R2]

| 事项 | 决策 |
|---|---|
| 会话启动、Worktree、终端、消息、运行状态、已有恢复 | 沿用 Orca；只验证接入是否可靠 |
| Git 差异查看、分支操作、现有通知和日志界面 | 沿用；不另做工作台 |
| 旧 kit 的目录规则、提交与集成检查、既有测试样例 | 优先迁移；不为统一语言或形式而全部重写 |
| 并行计划是否合理、写权是否冲突、何时接纳成果 | 是新增功能的核心 |
| 身份平台、消息总线、独立调度器、计费平台、插件市场 | 不进入主线最低范围 |
| 执行器 SDK 适配 | 先复用 Orca 支持；确有能力缺口再补，不提前另建三套驱动 |

每个新增需求先回答：上游已有能力能否直接使用？通过现有配置能否满足？只有剩余缺口才作为二开内容。

## 三、版本总览

| 版本 | 首要问题 | 最低成果 | 用户阶段 |
|---|---|---|---|
| v0.1 | 三模块能否在 Orca 上闭环？ | 一仓库、一成熟执行器、少量独立 Worker 的真实交付 | 自用，熟人观察 |
| v0.2 | 出问题时是否可控、可解释？ | 失败不乱、有限恢复、人工接管、可安装试用 | 3–5 名开发者定向内测 |
| v0.3 | 离开你的机器和工具是否仍有效？ | 两种执行器、两个仓库、可复用协作配置 | 5–10 名目标开发者 |
| v0.4 | 能否产出有业务价值的软件？ | OpenDashboard 一个真实只读场景与可独立部署产物 | 1–2 位行业共创伙伴 |
| v0.5 | 第二次交付是否更省事且可维护？ | 第二次复用、差异配置、兼容与升级恢复 | 同一细分场景的第二次交付 |
| v1.0 | 能否持续对外提供而非依赖作者陪跑？ | 稳定发布、明确支持范围、独立使用与持续维护 | 扩大正式使用 |

以上人数是建议规模，不是统计显著性标准，也不是获客承诺。

## 四、v0.1：Orca 二开的最小可行版

### 目标

在现有 Orca 中启用一套受约束协作方式，让一个真实的小需求经过拆分、隔离执行和结果整合。使用你已经熟悉的 Codex 接入，先覆盖一套环境、一种仓库、一种执行器；验证时使用 2–3 个开发 Worker 即可，这不是架构数量上限。

### 必须具备

| 功能 | 最低可接受行为 |
|---|---|
| 明确目标与验收 | 开始前知道要完成什么、什么不在本轮范围内；人可以确认或修改 |
| 按现有边界拆任务 | 每项任务有目标、负责范围、依赖和验收；可合并、串行，不为增加 Agent 而拆分 |
| 独立执行 | 复用 Orca 创建或管理独立会话、Worktree 与分支，不要求改造原仓库结构 |
| 有限接触与求助 | Worker 得到必要上下文；跨范围修改先请求协调，不默认全员广播，也不把信息彻底封死 |
| 范围与成果检查 | 对实际改动和集成候选进行检查；不能只相信 Agent 自述完成；越界和失败成果不得自动进入主线 |
| 人工确认交付 | 区分报告完成、验收通过和已合入；最终提交或发布由用户确认 |
| 基本失控保护 | 有并发、任务追加和重试的边界；能停止继续派发；无法确认状态时停下求助并保护已有成果 |
| 最小记录 | 保存目标、关键分工、结果、失败与人工干预；不建设专用分析平台 |

Orca 原生有效完成消息会改变任务生命周期，因此新增验收不能仅依靠原生“完成”状态。[R2]

### 可以人工做

选择目录划分、确认计划、裁决共享接口、审核最终成果、处理超出支持范围的异常。

### 不能人工代替后再声称功能完成

长期手动搬运所有子任务、手动核对每次越界、亲自修好所有分支才合并，然后把结果记成内核自主完成。人工修正必须记录。

### 本版不做

新 IDE、独立调度器、完整故障自愈、多级自治递归、远端集群、全操作系统支持、行业模板平台、进化引擎、商业计费。

### 放行条件

完成至少两类小型真实任务，其中一类含共享契约或先后依赖；已设定的越界、测试失败和集成失败样例被拒绝；正常结果可经用户确认进入目标分支。关闭新增模式后仍可按普通 Orca 工作方式使用。

没有与旧 kit 相比的确定收益时，可以继续验证使用便利性，但不得以增加 Agent 数量代替结果改善。

## 五、v0.2：可控的开发者内测版

### 目标

让少量外部开发者能够在明确边界内试用。无需保证所有任务无人值守成功，但失败必须可见、可停止、可接手。

### 必须增加

| 功能 | 最低可接受行为 |
|---|---|
| 安装与前置检查 | 说明支持的 Orca、执行器、环境和仓库条件；启动失败指出缺什么，避免反复猜命令 |
| 可理解的进度 | 区分执行中、等待依赖、等待回答、等待验收、失败、状态不确定 |
| 有限重试与局部继续 | 可以仅重试失败任务；保留已验收成果；恢复复用 Orca，不确定时交回人工 |
| 重复与过期结果处理 | 重复报告不重复合并；旧任务结果不会解锁新任务；不能把旧 Worker 未停止当作新建写入者的许可 |
| 人工接管与计划变更 | 用户可暂停派发、修改范围或取消任务；说明哪些下游成果需重验 |
| 可控资源和费用 | 至少限制并发、任务次数、时长和重试；精确费用不可得时明确标未知，不显示虚假零成本 |
| 内测诊断与隐私 | 用户选择是否导出诊断；默认不收集完整源码、密钥或客户数据；披露外部模型数据流 |
| 保护已有工作 | 不自动覆盖未提交修改、不默认清理未知工作区；停止执行与删除成果分开 |

### 可以延后

全自动恢复、完整费用结算、全平台安装体验、新仪表盘、复杂多人组织权限。可先由你做一次安装辅导，但用户后续任务不应次次依赖你操作。

### 本版不做

承诺可运行任意不可信代码；开放接管生产主机；自动上线客户系统；大规模开放注册。

Worktree 共享部分仓库信息，它是开发工作区机制，不是单凭使用就得到的恶意代码沙箱。[R3]

### 放行条件

建议邀请 3–5 位有真实仓库的开发者。至少两位在初次辅导后，各自完成两轮任务；重启、中断、重复完成和旧结果回报等预设异常没有错误接纳或覆盖已有工作。未完成时能清楚说明阻塞点和接手方法。

这些是小样本产品门槛，不是普遍可靠性证明。

## 六、v0.3：跨执行器、跨仓库的可复用版

### 目标

验证项目不只在你的机器、Codex 和手工准备的仓库里有效。第二个执行器优先 OpenCode，通过 Orca 原有接入验证，而不是另建平行运行系统。

### 必须增加

| 功能 | 最低可接受行为 |
|---|---|
| 第二种执行器 | Codex 与 OpenCode 均能完成同一类协作任务，核心规则不需重写 |
| 不依赖原生子 Agent | 通过独立会话完成协作，不把宿主原生子 Agent 作为必须前提 |
| 差异可见的能力支持 | 明确取消、恢复、日志、结构化结果和用量能力；不支持的能力拒绝或采用有说明的降级 |
| 可复用仓库接入配置 | 保存所有权、共享契约、验收与执行偏好；新仓库无需重构成指定布局 |
| 受控追加与调整任务 | 新需求先经过边界、依赖和资源检查；影响局部时不重跑整个项目 |
| 增量开发 | 在上次已验收成果上继续修复和扩展，而不只是每次从零生成 |
| 有界扩展 | 任务可排队和增加 Worker，但并发受预算与资源控制；公布实测配置而非无限规模保证 |
| 非文件冲突处理 | 对支持范围内的端口、测试数据库等共享资源避免双占；不把它扩展成通用资源平台 |

### 选择性增强

同一任务流程混合两个执行器、多个层级的委派、额外执行器、更多仓库布局。至少验证跨执行器接替一项任务；上下文交接基于成果和必要说明，不要求不同工具无损复制会话历史。

### 本版不做

任意 SDK 自动兼容、所有语言分析、无限递归、跨区域集群、大型企业统一账号平台。

### 放行条件

两个结构不同的真实仓库、两个执行器均完成闭环；至少一个仓库不是你预先手工整理的专用样板；执行器切换不导致越权或重做全项目；至少有用户主动再次使用。

规模测试用不同并发配置观察质量、人工与资源变化，不预先承诺并发增加一定加速。

## 七、v0.4：OpenDashboard 首个行业试交付版

### 目标

用 kernel 交付一个真实用户愿意反复使用的软件闭环。内核功能继续围绕通用开发协作，行业逻辑留在行业能力包和交付软件中。

当前 OpenDashboard 保留确定性 Fixture 与静态可信插件，公开主线尚无 Live provider；现有候选是显式启用、只读、仅 loopback 的本机健康适配器。[R4] 可以从这里完成技术验证，但最终行业选择由可接触用户、可获得数据和明确验收共同决定，不只由现有页面决定。

### 必须增加

| 功能 | 最低可接受行为 |
|---|---|
| 一个有限业务闭环 | 一位明确使用者、一个高频问题、一套验收；不以“完整企业平台”作为需求 |
| 一个真实且授权的数据源 | 初次只读接入；字段含义、单位、时间和质量状态明确；不在失败时伪装成正常 |
| Fixture 与 Live 分离 | 样例继续支持回归和演示；真实失败不能偷偷使用样例兜底 |
| 可用的业务流程 | 有真实信息展示、状态/规则与必要人工操作；规则范围以场景需求为准 |
| 开放接口 | 至少一个有说明、有输入输出样例、能由外部调用验证的接口；不等于暴露全部内部实现 |
| 第一份能力包 | 聚合已有模块、配置、契约、业务样例与验收；可以先随仓库保存，不建设市场 |
| 独立部署 | 交付物不依赖 Orca 或 coding agent 运行；使用者能配置、启动、停止和查看故障 |
| 最小真实使用保障 | 按需要提供持久化、访问控制、密钥分离、日志和备份恢复；不能把必要保护当未来增强 |

### AI 的位置

建议 OpenDashboard 首个包采用确定性业务核心、AI 可选增强，使模型不可用时基础观测和人工流程仍可用。框架本身不强迫所有产品如此：AI 原生能力包可以依赖模型，但必须声明依赖、失败表现和可用的替代流程，不能宣称所有功能都能离线运行。

### 用户与范围

邀请 1–2 位有实际流程和样例数据的行业共创伙伴。访谈和数据准备提前进行，真实试用在本版就开展，不等 v1.0。先以单客户独立部署控制范围。

不做自动设备控制、多租户 SaaS、通用低代码平台、几十个协议或任意第三方插件热加载。若真实试点涉及 LAN 或远端输入，必须重新确认范围，不能沿用 loopback 试验的批准。

### 放行条件

外部用户使用真实授权数据完成实际工作；交付物在没有开发工具的环境运行；断线、异常输入、重启和所需备份恢复有明确结果；一个第三方调用方或独立测试程序可以按说明调用开放接口。

## 八、v0.5：二次复用与维护验证版

### 目标

证明不是用 Agent 做了一次定制项目，而是形成可反复使用的行业交付资产。优先找同一细分行业的第二客户或第二数据源，不急于跳到完全无关的行业。

### 必须增加

| 功能 | 最低可接受行为 |
|---|---|
| 第二次有差异的交付 | 使用同一基础模块解决另一真实输入、客户配置或流程差异 |
| 差异分类 | 区分配置、适配器、必要定制代码；不为每个客户复制整仓库 |
| 能力包版本与兼容范围 | 明确它适配哪个应用壳、接口与配置；不兼容时提前报告 |
| 更新影响识别 | 模块或契约变化时指出受影响能力并重新验收 |
| 升级和恢复 | 至少验证上一版本升级；配置和数据可迁移或恢复，不能把恢复旧程序等同于恢复数据 |
| 客户边界 | 每个交付环境权限、密钥、数据和日志隔离；单客户部署不等于无需授权 |
| 交付与退出 | 有部署、运维、已知限制与数据导出说明；客户不被某一段 Agent 会话绑住 |
| 复用证据 | 记录第二次新增了什么、复用了什么、人工与维护成本，不能用代码总量冒充复用价值 |

### 可以延后

跨行业统一模型、插件商店、在线计费、复杂配置语言、所有历史版本迁移。

### 放行条件

至少两次可区分的交付共用同一套已验证基础；第二次没有偷偷复制重写核心；完成一次升级及恢复验证；至少一位外部使用者能照文档完成部署或维护动作。

如果第二次仍近似重做第一套项目，应调整能力包边界或选窄场景，不进入“通用平台化”。

## 九、v1.0：明确支持范围内的稳定目标版

### 目标

把前面已验证的闭环变成可持续对外提供的产品。v1.0 主要是稳定承诺，不是又增加一批宏大功能。

### 必须补齐

| 功能 | 最低可接受行为 |
|---|---|
| 支持矩阵 | 明确环境、Orca 基线、执行器版本、仓库类型、并发条件和已知限制 |
| 稳定发布与兼容验证 | 上游升级先验证再采用；二开构建可识别，避免误更新回原版；有恢复路径 |
| 统一交付状态 | 用户分得清执行完成、验收通过、合入与发布，失败原因可定位 |
| 自助使用与支持材料 | 安装、接入、运行、接管、反馈、升级流程无需作者持续远程操作 |
| 权限与数据承诺 | 定义开发期和交付期边界、日志外发与保留规则、外部模型数据范围；越界任务拒绝 |
| 可用性和回归 | 已列异常场景持续验证，不回退旧 kit 已有保护；修复不能只在单次演示有效 |
| 来源与维护责任 | 保留复用来源与所需声明，明确产物、环境和业务数据由谁维护 |
| 真实用户价值 | 外部开发者重复使用，行业伙伴愿意继续用；把人工、成本、质量的实际数据说清楚 |

### 最低目标画像

至少两种执行器、两种已验证仓库样例、一个可交付行业能力包、一次有实质差异的复用与升级，形成真实记录。不是要求全行业覆盖。

有这些功能却没有持续使用者，不能靠改版本号证明产品成立。反过来，前期已有用户愿意付费且范围适当，也不必等编号到 v1.0 才验证商业价值。

## 十、v1.0 之后：进化路线

### v1.1：经验辅助与离线策略优化

目标：减少同类任务中的重复错误与无效协调，不让系统擅自更改自身规则。

必须具备：有来源和适用范围的案例复用；用户授权后的经验保存与删除；只优化任务说明、拆分粒度、执行器选择或上下文组织中的少量对象；在固定任务上比较新旧策略；独立保留验收集；人工批准启用；策略可回滚；实验受独立预算约束。

第一步选择一个优化目标即可，不同时优化全系统。GEPA 当前提供基于评估反馈的优化能力，可以作为后续复用对象，不需要自建全套演化优化器。[R5]

放行：在独立保留任务上没有突破安全与质量底线，且人工、成本或完成质量至少一项有重复可见改善；不是只提升训练样例分数。缺少足够案例时，只提供检索辅助，不强行上线优化。

### v2.0：有边界的持续改进

目标：在明确可评估的任务上，生成多种候选、独立验证、选择更好的方案，再通过原交付流程使用。

必须具备：区分互补任务的合作整合与同题候选的竞争选择；固定候选的权限与评估标准；实验和正式运行分离；保留评估证据、费用与失败记录；退化可撤回；获胜候选也走正常验收和批准。

不允许实验自动扩大预算、读取其他客户经验、修改测试标准、降低权限门槛或自行发布生产变更。不因为存在候选搜索就宣称整个 kernel 已能可靠自我改写。

## 十一、嵌入式扩展：按真实设备需求分层

| 阶段 | 最低功能 | 前提与边界 |
|---|---|---|
| H1 软件侧只读接入 | 一个实际设备或现成网关、一个明确协议、断连和数据质量处理 | 可以在 v0.4/v0.5 由客户需求触发；复用协议和网关 |
| H2 开发工具链适配 | 一个目标板卡和工具链、编译/仿真/真机结果分开、烧录和测试设备互斥占用 | 核心运行稳定后推进；模拟或编译不代替真机验收 |
| H3 受控设备操作 | 明确授权、人工批准、执行结果确认、超时和失败处理、恢复与安全限制 | 独立风险和现场验收；不沿用只读权限直接扩展 |

Orca 和开发 Agent 留在开发机或构建环境，客户软件运行在服务端/网关，固件在目标设备。不是把同一套桌面环境塞进所有 MCU。

H1 可以先于 v1.0；H2/H3 是否进入更后版本，取决于真实使用者和验证条件，不应该成为整个 kernel 发布的强制前提。

## 十二、内测与商业验证

### 两种用户不要混在一起

开发者内测回答：分工是否容易理解？失误是否减少？是否愿意第二次使用？可以接受终端，但不能每次都靠作者修状态。

行业共创回答：真实问题是什么？数据能否授权提供？功能是否解决工作？能否部署与维护？不要求对方理解 Worktree 或多 Agent。

现在同步访谈少量两类用户；v0.2 启动开发者试用；v0.4 启动真实业务试点。

### 每次内测只收集必要证据

目标和验收；起始项目与工具版本；实际结果；人工介入；总耗时和可观测费用；错误/返工；用户是否主动再次使用。源码和客户数据不作为默认反馈附件。

招募时明确支持环境、费用由谁承担、模型数据流、允许使用的仓库范围和停止方法。优先非关键分支、脱敏样例和非生产环境；需要敏感或不可信执行时另设保护门槛。

### 建议控制定制请求

一次只确定一个共创场景的完成标准。单个用户的专属请求先留在配置、适配器或明确定制里；重复出现并经验证的共性需求才进入内核。不要为了赢得每个潜在用户不断扩充首版。

## 十三、贯穿全程的遗漏风险

### 1. 需求质量

开始前必须能回答“谁用、什么输入、什么结果、谁验收”。允许需求未明时停止执行或返回澄清，不让 Agent 自动填补关键业务事实。

### 2. 原生功能、用户直改与受管模式冲突

内核保证只针对声明受管的流程。用户直接操作普通 Orca 或修改仓库时，需要明确哪些成果还要重验；不能假设所有入口天然受控，也不能禁止用户接管自己的项目。

### 3. 成本显示不等于预算控制

无法准确获取订阅或模型费用时，使用执行次数、时长与并发等可验证边界；不得把估算当财务账单或硬性消费上限。

### 4. 故障恢复不等于重开 Agent

旧进程状态未知时先核实，避免两个写入者。不能恢复时，给出保留成果和接管办法；安全地停下是合格结果。

### 5. 过度拆分

小任务允许单 Agent 或串行；并行收益不明确时，不为框架宣传强制多 Agent。

### 6. 流程本身的负担

将配置时间、阅读报告和被打断次数计入人工成本。若多 Agent 工具让使用者先维护一堆文档、状态或平台，说明应削减流程而非继续加功能。

### 7. 上游维护

固定可用基线，窄范围二开，明确升级兼容和退回方式；不随上游每次变化中断用户运行。现有能力能替代自研扩展时，优先减少维护面。

### 8. 对外承诺

不说支持任意 SDK、任意行业、无限并发或绝对安全。分别列出已验证、实验、未支持的范围。完整测试通过也不等于对全部任务的普遍可靠性保证。

### 9. 开发期 AI 与业务期 AI

开发使用 AI 是工具链选择；交付物是否依赖模型是业务设计。不得默认向客户运行时引入开发工具和密钥。

### 10. 退出能力

用户应保留代码、成果和业务数据的可导出性。停止使用 kernel 后仍能用普通 Git/开发工具维护交付物；客户停用 AI 后的行为应与声明一致。

## 十四、评估与转向门槛

比较对象：单上下文；配置合理的原生多 Agent；旧 kit；新 kernel。固定需求和最终验收，保存失败和人工修正。分别评估同预算下质量以及达到同质量所需的人工、时间和成本。小样本用于决策，不宣传普遍倍数提升。

| 阶段 | 值得推进的证据 | 缺证据时的动作 |
|---|---|---|
| v0.1 → v0.2 | 核心闭环真实成立，使用便利或约束有增益 | 修复最小闭环，不加行业与进化功能 |
| v0.2 → v0.3 | 有外部用户第二次使用，失败可接管 | 优先修接入与可理解性，缩小支持范围 |
| v0.3 → v0.4 | 可跨执行器/仓库复用，协调负担可接受 | 查明是否只适合固定模板，不承诺通用 |
| v0.4 → v0.5 | 行业用户实际使用且愿意继续 | 调整业务问题，不能靠加 Agent 挽救需求 |
| v0.5 → v1.0 | 第二次复用和升级成立 | 收窄行业或保留定制服务，不急平台化 |
| v1.0 → v1.1 | 已有足够可比较案例与确定的重复损失 | 保持稳定工具，暂缓进化 |

## 十五、下一阶段的范围冻结

现在仅冻结 v0.1 功能和验收；v0.2 是近期方向，v0.3 以后保留目标并根据内测调整。开发主线一次推进一个主要问题，用户访谈与验收准备可以并行，但不同时展开多个平台的建设。

第一版的判断句：一个真实需求，在现有 Orca 中，以少量独立 Agent 按明确边界完成；越界与失败不能混入成功结果；人能够审查、停止并保留成果。

做到后马上进入小范围试用，不等“最终架构”完成。
